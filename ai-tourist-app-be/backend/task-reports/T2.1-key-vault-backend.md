## Summary

Implemented the T2.1 Key Vault Backend per Issue #25: a JWT-protected REST
service that stores user-encrypted AI provider key blobs (ciphertext + iv +
auth_tag), supports per-row CRUD keyed by the row UUID, and exposes a
`POST /keys/:id/validate` endpoint that runs a single provider-specific test
call against the user's plaintext key and updates `is_valid` / `validated_at`.
The server never decrypts the stored blob; the plaintext is held in a Buffer
for the duration of one fetch only and then zeroed.

## Sub-tasks completed

### Task 2.1.1 — Key Vault Endpoints

| Endpoint | Behaviour |
|---|---|
| `POST /keys` | Upsert `(user_id, provider)` → `(ciphertext, iv, authTag)` |
| `GET /keys` | List user's keys — metadata only |
| `GET /keys/:id` | One key's metadata (UUID) |
| `DELETE /keys/:id` | Delete by id, scoped to owner |
| `POST /keys/:id/validate` | Single provider test call; updates `is_valid` + `validated_at` |

All endpoints sit behind `requireAuth` (JWT bearer). Id-keyed (UUID) rather
than provider-keyed, so the same user can have multiple keys per provider
(future-proofing) and the validate endpoint can address a specific stored
key.

### Task 2.1.2 — Key Validation Endpoint

`POST /keys/:id/validate` accepts `{ plaintext: string }` in the body. The
service:

1. Loads the encrypted blob scoped to the owner.
2. Dispatches to a provider-specific validator via `validateKeyForProvider`.
3. Updates `is_valid` and `validated_at` in `api_keys`.
4. Returns `{ isValid, reason?, validatedAt, provider }` — **never** the
   plaintext, never the blob.

Provider test endpoints (a single GET/POST per provider, smallest valid
request that proves auth):

| Provider | URL | Method | Auth header |
|---|---|---|---|
| `openai` | `https://api.openai.com/v1/models` | GET | `Authorization: Bearer …` |
| `openai-compat` | `{base}/v1/models` (override) | GET | `Authorization: Bearer …` |
| `anthropic` | `https://api.anthropic.com/v1/messages` | POST (model+max_tokens=1) | `x-api-key: …` |
| `google-genai` | `https://generativelanguage.googleapis.com/v1beta/models` | GET | `x-goog-api-key: …` |
| `xai` | `https://api.x.ai/v1/models` | GET | `Authorization: Bearer …` |

Status → outcome mapping:
- 2xx → valid
- 401/403 → invalid (unauthorized)
- 400 (anthropic specifically) → invalid (provider rejected request)
- 5xx / network error / timeout → invalid with reason

### Task 2.1.3 — NEVER decrypt on server (CRITICAL)

Enforced at three layers:

1. **Schema** (`keyVault.schema.ts`): no field in any request returns a
   decrypted value. Response types `StoredKeyMeta` only carry metadata.
2. **Service** (`keyVault.service.ts`): `getKeyMeta` / `listKeyMeta` /
   `deleteKey` only `SELECT` the non-ciphertext columns. `validateStoredKey`
   is the *only* path that reads the blob, and it does so via an internal
   `fetchBlobForOwner` that is not exported and never returns the plaintext.
3. **Validator** (`keyValidator.ts`): the plaintext is held in a
   `Buffer.from(plaintextKey, 'utf8')` and `keyBuf.fill(0)`-ed in a
   `finally` block, so the in-memory copy is wiped deterministically before
   the function returns.

Tests explicitly assert the plaintext never appears in the validate
response body (`POST /keys/:id/validate › never returns the plaintext or
the ciphertext blob in the response`).

## Concerns

1. **Pre-existing `auth.test.ts` failures (7 cases)** — caused by the
   working tree containing in-progress Sprint 3 auth refresh-token-rotation
   work that another agent had partially applied but not yet finished
   (uncommitted edits to `auth.service.ts`, `auth.routes.ts`,
   `auth.schema.ts`, `auth.test.ts`, plus a new migration
   `004_refresh_tokens.*`). These tests reference a `refresh_tokens`
   table that the fake does not yet model for some queries (`UPDATE
   refresh_tokens SET revoked_at = now() WHERE user_id = $1`, the
   `FOR UPDATE` lock, etc.). They were failing BEFORE my changes and are
   outside the scope of T2.1. **Recommend the Sprint 3 auth task own the
   fix** — adding additional handlers to my keyVault test setup would
   cross scope boundaries.
2. **Pre-existing TS/lint warning**: `auth.service.ts` line 24 imports
   `AuthTokens` but never references it (`@typescript-eslint/no-unused-vars`).
   Pre-existing in the WIP, not introduced by T2.1.
3. **`api_keys.id` is a UUID PK** — the validate endpoint's `idParamSchema`
   requires a UUID, so clients must use the id returned from `POST /keys`
   or `GET /keys`. This is fine for the frontend which calls these in
   sequence, but if any client tries to validate by provider name they'll
   get a 400 — by design, since the validate endpoint needs a specific
   stored row.
4. **No integration tests with a live Postgres** — per backend-agent.md
   self-test rules (DB is mocked, no live network). The migration is
   unchanged from Sprint 1 (`001_init.up.sql` already defines the
   `api_keys` table with the exact columns we read/write), so a real
   migration run will Just Work.
