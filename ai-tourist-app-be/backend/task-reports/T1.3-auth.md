# Task 1.3 — Auth (email + password + JWT) [BE + FE] (Issue #24)

**Status:** DONE
**Branch:** `feature/auth/sprint1`
**Date:** 2026-09-25

## Summary

Implemented end-to-end email/password auth for the AI Travel Guide: a
backend with bcrypt-hashed credentials, JWT access tokens (15-minute TTL)
plus refresh tokens (7-day TTL) with rotation and replay-detection, and a
frontend with login/signup screens, protected routes, Zustand session
store, and a transparent Axios refresh-on-401 interceptor. The optional
Google social-login path is scaffolded as a documented stub for the next
sprint.

## Sub-tasks completed

### Task 1.3.1 — Backend Auth Endpoints

| Endpoint | Behaviour |
|---|---|
| `POST /auth/signup` | Create user with bcrypt-hashed password (cost 12); returns access (15m) + refresh (7d) tokens |
| `POST /auth/register` | Alias for `/signup` (backward-compat with the placeholder route) |
| `POST /auth/login` | Validate credentials; return access + refresh tokens; persist refresh row |
| `POST /auth/refresh` | Rotate the refresh token: revoke old `jti`, issue a new pair; replay-detection revokes the whole family |
| `POST /auth/logout` | Revoke the supplied refresh token (idempotent) |
| `GET /auth/me` | Returns the authenticated user's profile (JWT-protected) |

Errors:
- Duplicate email → `409 EMAIL_TAKEN`
- Wrong credentials → `401 INVALID_CREDENTIALS`
- Expired/invalid refresh → `401 INVALID_REFRESH`
- Refresh replay → `401 REFRESH_REPLAY` + family revocation

JWT scheme:
- Access token (HS256, 15m, `JWT_ACCESS_SECRET`), payload `{ sub, type: 'access' }`
- Refresh token (HS256, 7d, `JWT_REFRESH_SECRET`), payload `{ sub, jti, type: 'refresh' }`
- Refresh tokens are persisted in `refresh_tokens` table; rotation
  writes `replaced_by_jti` and `revoked_at`; replay of a revoked `jti`
  revokes every active token for the user.

### Task 1.3.2 — Backend Unit Tests

35 auth tests in `src/__tests__/auth.test.ts`:
- Signup success, password hashing, bcrypt cost 12, duplicate-email
  conflict, refresh-token row persistence.
- Login success, refresh-token persistence, wrong password, unknown
  user (same error message — no enumeration).
- Refresh rotation: new tokens issued, old `jti` revoked, replay
  rejected + family revoked, wrong-secret rejected, garbage rejected.
- Logout: revoke on supplied token, idempotent on no body / garbage.
- `getMe`: profile returned for valid bearer; 401 without bearer;
  rejects access tokens signed with the refresh secret.
- Supertest endpoint coverage for every route (201/200/401/409/204
  status codes; payload shape).

Total backend test suite: **154 tests passing across 9 suites.**
Mock DB (`createFakeDb`) keeps the suite hermetic — no live Postgres
required.

### Task 1.3.3 — Frontend Auth

Files added:
- `src/auth/types.ts` — `AuthTokens`, `AuthSession`, `AuthError`,
  `AuthResponse` (pre-existing — kept).
- `src/auth/tokenStorage.ts` — `localStorage` helpers with safe
  fallbacks for SSR / disabled-storage contexts.
- `src/auth/api.ts` — Raw axios client that talks to the backend
  `/auth/*` endpoints (deliberately does NOT use the shared
  `httpClient`, so the 401-refresh interceptor doesn't fire on
  legitimate auth failures like `/auth/login` rejecting bad creds).
- `src/auth/store.ts` — Zustand store: `login`, `signup`, `logout`,
  `refreshSession`, `applyRefreshedTokens`, `clearError`. Persists
  tokens to `localStorage`; reads them back on boot via
  `bootstrapAuth`.
- `src/auth/AuthPage.tsx` — Real login/signup tabs with form
  validation (email format, ≥8-char password, optional display name),
  ARIA-friendly error messages, loading state, and a redirect on
  success.
- `src/core/http.ts` — Bearer-token request interceptor + 401
  refresh-on-401 response interceptor with **single-flight rotation**
  (concurrent 401s share one refresh promise to avoid races), retry
  flag to prevent loops, and short-circuit on `/auth/*` endpoints.
- `src/core/router.tsx` — Removed the placeholder `void useAuthStore`
  shim now that `AuthPage` issues real login calls.
- `src/components/AppLayout.tsx` — Shows email + logout button in the
  header when authenticated.
- `src/main.tsx` — Calls `bootstrapAuth()` on app start so a hard
  reload with stored tokens resumes the session.
- `src/auth/index.ts` — Public surface: `useAuthStore`, `AuthPage`,
  `authApi`, `bootstrapAuth`, `resetAuthStoreForTests`, plus the
  Google stub exports.

Frontend tests (vitest + Testing Library):
- `api.test.ts` — 13 tests covering signup/login/refresh/logout/getMe
  payload shape and error mapping.
- `store.test.ts` — 16 tests covering login/signup/logout/refresh
  flows, `bootstrapAuth`, and `applyRefreshedTokens`.
- `AuthPage.test.tsx` — 10 tests covering tab switching, validation,
  error surfacing, redirect on success, and error-clearing.
- `tokenStorage.test.ts` — 7 tests covering read/write/clear and
  failure-tolerant access.
- `http.test.ts` — 7 smoke tests confirming the shared client
  exposes the axios surface area and the interceptor managers are
  registered.
- `AppLayout.test.tsx` — Extended with 3 tests for the
  email/logout-button visibility + logout action.
- `google.test.ts` — 2 tests for the stub module.

Total frontend test suite: **143 tests passing across 17 files.**

## Notes for the next sprint

   backend `POST /auth/google` accepting an ID token.
2. Refresh-token storage currently uses `localStorage` for convenience.
   For the highest-security posture, consider moving to `httpOnly`
   cookies + a CSRF token — see the design doc for the trade-off.
3. The 401-refresh interceptor is a smoke-tested module; the
   end-to-end refresh flow is exercised against the live backend in
   the manual QA pass for this issue.
